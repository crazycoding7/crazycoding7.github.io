1. 基础

1. 关键字 空安全(Sound NullSafety)、late、required、??、! 等

  • 空安全

    是一种通过类型系统在编译时彻底杜绝空指针异常的一种特性。相比于 Java 的手动防御和 TypeScript 的非健全设计，Dart 和 Kotlin 提供了真正安全、可靠且不影响开发体验的空安全机制。

    例子： 接口字段频繁变更问题：实体类字段都为空DTO，业务Model做转换(集中处理脏数据和默认值)。好处：UI层彻底解放、容错集中化；坏处：多Model类和转换。

  • late 解决非空变量无法立即初始化问题(LateInitializationError)

  • ?? 默认值

    Text(user?.name ?? ‘未知用户’)

  • ! 强制告诉编译器：“我保证这个变量此时绝对不为 null”。

  • Mixin（with混入） 是横向扩展

    Dart 语言不支持多重继承（即不能写 class C extends A, B {}），为了解决单继承的限制并避免多重继承带来的“菱形问题（Diamond Problem）”，Dart 引入了 Mixin。通过 Mixin，一个类可以同时拥有多个不相关类的功能。

  • Sealed Class（密封类）

    Enum 适合表示固定的“标签”，而 Sealed Class 适合表示固定的“状态机（包含不同的数据载荷）”。

  • 模式匹配（Pattern Matching）

    在 Dart 3 中，它其实是一个语法类别，就像我们平时写的 if 语句或 + 表达式一样。它的核心能力可以拆分为两个动作：匹配（Matching） 和 解构（Destructuring）。

2. 线程、消息

​ Flutter 引擎底层有 4 个线程(UI、渲染、平台、IO)，但开发者编写的 Dart 代码只运行在 UI 线程上，采用单线程事件循环模型。async/await 只是在这个单线程内调度任务，并非开启新线程。如果遇到解析大 JSON 等 CPU 密集型任务阻塞了 UI，我会使用 Dart 提供的 Isolate 机制。Isolate 拥有独立的内存和事件循环，不共享内存，通过消息传递通信，从根本上避免了锁竞争和线程安全问题，是 Flutter 中实现真正并行的核心武器。

4. 异步

在 Dart 中，async 和 await 并不是魔法，它们本质上是 Future 的语法糖，其底层完全依赖于 Dart 的单线程事件循环（Event Loop）和消息调度机制来实现异步。

1. async：函数的“包装器”与状态机**

当你把一个函数标记为 async 时，Dart 编译器在底层会做两件事：

  • 自动包装返回值：无论函数内部返回什么，它都会被包装成一个 Future 对象。
  • 生成状态机：编译器会将 async 函数内部的代码逻辑转换为一个状态机（State Machine）。当函数执行时，它会同步运行直到遇到第一个 await 关键字。

2. await：挂起与消息入队**

当代码执行到 await someFuture 时，消息机制开始发挥核心作用：

  • 挂起当前执行：await 会立即“挂起（Suspend）”当前 async 函数的执行，并将函数的控制权交还给调用者。这意味着 await 后面的代码不会立即执行，也不会阻塞主线程。

  • 注册回调（消息入队）

    Dart 会在 someFuture 完成时，将 await后面的代码作为一个回调任务进行调度。根据 Future

    的状态，这个任务会被放入不同的队列中：

    • 如果 Future 已经执行完毕，后续的代码会被放入微任务队列（Microtask Queue）。

  • 如果 Future 还在执行中（例如网络请求），后续代码会被放入事件队列（Event Queue），等待 I/O 操作完成后再被调度。

5. setState原理

6. Stream原理(StreamController/StreamBuilder)

核心机制：生产者与消费者的单向数据管道，分为单次订阅和广播流。

7. InheritedWidget

“InheritedWidget 是 Flutter 中实现跨组件状态共享的核心机制。它通过自上而下注入数据，并利用底层的 Element 树建立依赖关系。当数据变化时，它通过 updateShouldNotify 方法判断，仅通知依赖它的子组件进行精准重建，避免了全局刷新带来的性能损耗。同时，它也是 Provider 等主流状态管理库的底层实现基础。”

2. UI卡顿

​ 耗时时间计算： UI线程耗时：build-layout-paint-compositing; 渲染线程耗时。

​ 业界标准：

  1. 当前帧耗时 > 前3帧平均耗时 × 2
  2. 当前帧耗时 > 83.3ms（两帧电影帧耗时，即 1000÷24×2≈83.3ms）

若帧耗时进一步超过 125ms（三帧电影帧耗时），则判定为 BigJank（严重卡顿）。

等级 判定条件 处理策略
正常 100帧内 Jank 帧数 = 0 无需关注
轻微 100帧内 Jank 帧数 = 1 记录日志，周报汇总观察趋势
需优化 100帧内 Jank 帧数 = 2~3 标记为”关注页面”，纳入优化清单
严重 100帧内 Jank 帧数 ≥ 4 高优先级，限期整改
紧急 出现 BigJank（单帧 >125ms） 无论次数，立即排查

优化方式：

一、UI 线程优化（Dart 代码侧）

UI 线程负责 Widget 构建、布局计算、业务逻辑。优化核心是减少无效计算、缩小重建范围、异步化耗时操作。

1. 减少 Widget 重建

2. 项目问题解决

  • 一、问题本质

我在做 AI 流式对话时遇到一个性能问题：大模型通过 SSE 协议流式返回数据，SSE 是基于 HTTP 的长连接，服务端会持续向客户端推送数据块。

问题在于，SSE 的推送频率是不可控的，短时间内可能连续推送多个 chunk。如果每个 chunk 都直接触发 UI 更新，就会导致 Flutter 在一帧内多次 setState，进而引发频繁 build、diff、layout，甚至导致卡顿。

同时产品还要输出效果有节奏感——每行由慢到快线性加速显示。这就多了一层复杂度：网络给数据的速度和 UI 展示的速度是两回事，怎么协调？

二、方案分析

我的方案分三层处理：

第一层：网络接收层——控制数据推送频率

SSE 流式数据过来后，我不会每个 chunk 都直接 setState，而是先做缓冲和合并。按 30ms 的时间窗口数据合并，控制输出流频率。

这里 30ms 不是随便定的——60fps 下每帧约 16.6ms 的预算，30ms 大约两帧，既能降低高频 setState 带来的 build 压力，又能保持流式显示的连贯性。

第二层：状态管理层——控制刷新范围

这一层解决的是”谁该 rebuild、谁不该 rebuild”的问题。

我会把”正在生成的流式消息”和”已经完成的历史消息”分开管理。历史消息已经稳定，不应该因为当前流式消息更新而反复重建；只有当前正在生成的消息参与高频更新。

具体实现上，我封装独立的Text StatefulWidget 把每条消息的状态隔离开，里面用ValueNotifier控制刷新范围，确保更新最后一条消息时，只有最后一条 rebuild，历史消息完全不受影响。

第三层：UI 渲染层——控制显示节奏

产品希望打字机效果有节奏感，所以我在 UI 层的TextWidget单独做了一个打字机控制器，把网络层合并后的文本放进字符队列，按产品要求的节奏逐字出队显示。

节奏上我设计了每行独立的线性加速——每行第一个字符 83ms，最后一个字符 30ms，中间线性插值，换行时重置。这样视觉上就是”每行开头稍顿，然后越打越快”，节奏感很强。

三、代码实现（1 分 30 秒）

代码上我分三块来做：

第一块：网络层缓冲合并

网络层我做了个 30ms 时间窗口的事件合并。具体实现是用变量缓存上一轮的时间戳和累积的 JSON 数据串。每次收到新的 chunk 时，先和缓存的时间戳做差值比较：

  • 如果差值小于 30ms，说明还在同一个时间窗口内，就把新数据和缓存数据合并，继续等待
  • 如果差值大于 30ms，说明窗口已过，直接把合并后的数据发送给上一层，同时重置缓存、更新时间戳

这样 SSE 高频推送的多个 chunk 会被合并成一次更新，避免 UI 更新频率直接等于服务端推送频率。

第二块：刷新隔离

正在生成的消息 content 是独立的 RxString，用Obx包裹，TypewriterText 内部用 RxString.listen() 监听，只有当前这条消息在更新。历史消息的 Widget 完全不感知、不 rebuild。

第三块：打字机效果——行级加速 + 增量测量

  • 行级线性加速：每行独立计算，公式是 delay(i) = 83 - 53 * i / (N-1)，N 是这行的字符数。第一个字符 83ms，最后一个字符 30ms，换行时重置。延迟表按字符数缓存，相同字符数直接查表复用
  • 增量行测量：每次新内容到达，取「上一个缓存边界 → 文本末尾」这段交给 TextPainter 测量，调用 computeLineMetrics() 获取行信息。已确认的行把边界位置缓存到 _confirmedBoundaries 列表里，永不重测。即使回复几千字，单次测量也只涉及当前行这一小段
  • 一个工程取舍：第一行还没换行时，N 是未知的。当前方案用缓冲区长度近似，前几个字符的加速曲线会有轻微偏差，但差异在 13ms 以内，低于感知阈值，体感无影响

5. Flutter 插件开发原理

1. 插件注册机制（Platform Channel）

整体流程：

各角色职责：

角色 做了什么
Flutter Engine 启动时触发插件注册，调用 onAttachedToEngine
GeneratedPluginRegistrant 自动生成的”注册表”，把每个插件挂到 Engine 上
插件自己（你的 Kotlin/Swift 代码） 创建 MethodChannel，绑定 binaryMessenger，设置 Handler

2. 三种 Channel 类型

Channel 类型 通信方式 使用场景
MethodChannel 请求-响应（Dart → Native） 调用原生 API，如获取电量、调用相机
EventChannel 持续流（Native → Dart） 传感器数据、网络状态变化等持续推送
BasicMessageChannel 双向消息传递 自定义数据格式通信，如 JSON 字符串

3. 插件开发常见问题

问题一：Channel 名称不一致导致通信失败

  • 现象：Dart 侧调用方法，Native 侧收不到；或者 Native 回调了，Dart 侧没响应
  • 原因：Dart 端和 Native 端的 Channel Name 拼写不一致
  • 解决：统一使用常量定义 Channel Name，避免硬编码字符串

问题二：在 Channel 回调中做耗时操作阻塞主线程

  • 现象：调用 Native 方法后 App 卡顿，甚至 ANR（Android）或卡顿（iOS）

  • 原因：MethodChannel 的回调在 Android 和 iOS 上都运行在主线程。Android 是 Platform Thread = Main Thread，iOS 是 Main Queue。如果在回调中直接做耗时操作（网络请求、文件读写、数据库查询），会阻塞主线程

  • 解决：耗时操作必须切到后台线程执行，result 可以在任意线程回调（Flutter 内部保证线程安全）

问题三：插件注册时机问题——FlutterFragment/FlutterActivity 复用

  • 现象：页面重建后插件失效，Channel 调用无响应
  • 原因：FlutterEngine 被复用或重建，但插件没有重新注册
  • 解决：确保在 onAttachedToEngine 中正确初始化 Channel，在 onDetachedFromEngine 中释放资源

问题四：异步调用导致返回值丢失

  • 现象：Dart 调用 Native 方法后一直 pending，不返回
  • 原因：Native 侧方法有异步操作（如网络请求），但没有在完成后调用 result.success() 或 result.error()
  • 解决：确保所有代码路径都有 result 回调，包括异常分支

问题五：iOS 和 Android 行为不一致

  • 现象：同一个插件在 Android 正常，iOS 崩溃或无响应
  • 原因：两端平台线程模型不同，iOS 的 Flutter Engine 绑定在主线程，Android 可能在 Platform Thread
  • 解决：分别测试两端，注意 iOS 上不要阻塞主线程，Android 上注意线程切换

问题六：插件依赖冲突

  • 现象：集成插件后编译失败，报依赖版本冲突
  • 原因：多个插件依赖了同一个库的不同版本（如 Kotlin 版本、AndroidX 版本）
  • 解决：使用 resolutionStrategy 强制统一版本，或升级插件到兼容版本

问题七：热重载后插件状态丢失

  • 现象：Hot Reload 后 Native 侧状态丢失，需要重新初始化
  • 原因：热重载不会重新执行 Native 代码，但 Dart 侧状态已重置
  • 解决：关键状态放在 Native 侧持久化，或通过 setMethodCallHandler 重新绑定

4. 插件开发最佳实践

实践 说明
Channel Name 用包名限定 如 com.example.plugin/method，避免与其他插件冲突
定义清晰的接口协议 方法名、参数类型、返回值都要有文档
